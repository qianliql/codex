# 应用内更新与发布说明

轻账本从0.11.0开始支持在应用内检查、下载新版，再交给Android系统确认安装。0.10.2及更早版本没有此入口，首次升级到0.11.0仍需从[GitHub版本下载页](https://github.com/qianliql/codex/releases/latest)取得APK并覆盖安装。

## 用户如何更新

1. 打开“我的 → 设置 → 检查更新”。应用打开时也会定期检查新版本；每个新版本最多主动提示一次。手动检查可随时重试。
2. 查看版本变化，点“下载更新”。页面显示下载进度，完成后出现“安装更新”。
3. 首次从轻账本安装时，按照系统页面允许此应用安装更新；返回后由Android安装界面确认升级。系统不会静默安装。

如果网络暂时不可用，仍可照常使用账本，稍后重试或从GitHub版本页下载安装包。系统清除了应用缓存时，已下载的APK需要重新下载。原同签名版本可覆盖升级；遇到签名冲突应先导出并验证本地备份，避免卸载造成账本丢失。

## 版本来源与校验

应用读取公开仓库`qianliql/codex`的GitHub Releases `latest`接口。自动检查距离上次成功检查不足24小时会跳过；用户点击检查更新不受此间隔限制。只接受正式版本、较新的语义版本和更大的`versionCode`。每个正式版本须发布以下资产：

| 资产 | 用途 |
| --- | --- |
| `LightLedger-<版本号>-debug.apk` | 同一签名的Android安装包 |
| `app-update.json` | 安装包名称、版本、大小、SHA-256、最低系统版本和应用内更新说明 |
| `LightLedger-<版本号>-SHA256SUMS.txt` | 供用户在应用外核对下载文件 |

`app-update.json`使用`schemaVersion: 1`，字段为`versionName`、`versionCode`、`minSdk`、`apkName`、`sha256`、`size`和`notes`。`size`为APK字节数，`sha256`为64位小写十六进制摘要；`notes`是应用中显示的更新内容。版本文件须与GitHub Release标签、资产名称和大小一致。源码更新报告同时写在`docs/updates/<版本号>.md`和Release说明中。

应用只接受预期的GitHub仓库下载地址，以及GitHub下载过程中使用的HTTPS资产域名。下载后重新计算SHA-256，并检查APK包名、版本号、最低系统要求和签名是否与本机已安装的轻账本一致。验证失败会停止安装并提示重试。APK暂存在应用缓存的`updates`目录，通过受限`FileProvider`只向系统安装器提供读取权限。

`INTERNET`仅供读取公开版本信息和下载APK；`REQUEST_INSTALL_PACKAGES`用于打开系统安装流程。账单、备份、支付通知、OCR图片和诊断不会上传，也没有账号、广告或分析服务。版本检查不是服务器主动推送：GitHub上发布新版本后，用户下次打开应用或手动检查时读取最新信息。

## 每次发布的顺序

1. 更新`versionName`和递增的`versionCode`，完成源码、测试与同签名APK构建。报告记录实际验证范围及限制。
2. 计算最终APK字节数与SHA-256，生成匹配的`app-update.json`和`SHA256SUMS`；不要在这些文件或公开报告中放入账单、备份、真实通知、设备标识或私钥。
3. 推送源码、更新报告和版本标签，建立GitHub **草稿** Release。上传APK及两份校验资产，核对标签、文件大小、SHA-256和下载地址。
4. 所有资产齐全后再发布为最新正式版。发布后验证`releases/latest`返回该版本，应用内检查可读到版本文件，下载校验通过且系统安装界面可打开。

同签名覆盖安装和账本保留需要继续使用原交付签名；新的本地调试签名不能替代。若未来更换签名、仓库地址或版本文件格式，应先设计迁移路径，不能直接将不兼容APK推送给已安装用户。
